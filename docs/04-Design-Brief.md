# Restaurant demo sites — Design Brief

## Brand
- A sales/demo system, not one brand: each restaurant gets its own identity from its JSON (name, palette, type, hero variant). Reference `DESIGN.md` in the repo.
- **Voice:** neutral, local, trilingual; honest that these are previews.

## Color / type
- **Per-restaurant** palette and typography defined in each `data/restaurants/*.json` and realized by `src/components/Hero.astro` + `src/styles/global.css`. Accent hues are validated independently so two rooms can't share a color; dark near-black inks (e.g. Boi, Virgen) skip the hue check. Record each restaurant's exact hex values from its JSON when documenting an individual site.

## Component style
- Hero variants per cuisine (e.g. "cafeteria"), letterpress-style titles kept whole (no mid-word splits), accent bands that stay separated, menu sections, an hours line, an optional rating, and a sticky order bar with an ink top edge.

## Imagery
- Hero imagery per restaurant; 1200×630 PNG OG/share cards generated by `scripts/write-og.mjs`.

## Motion rules
- Minimal; hours line repaints every minute / on tab focus; scroll-into-view only on coarse pointers.

## Accessibility targets
- 44px link targets; legends on pickup/tip groups; per-dish Add names; live-region total; language-tagged text; contrast checked by `scripts/contrast.mjs`.

## Responsive breakpoints
- Mobile-first; order bar adapts on small screens.

## Reference sites
- Real local restaurant sites and delivery-app menus; `DESIGN.md` holds the system rules.

## What to avoid
- Making a demo look like the restaurant's official site (noindex, no third-party scores in structured data); sharing a palette between two rooms.

## Open questions
- Centralize per-restaurant palettes into one table in a future design-brief revision.
